# Benchmarks

## Reference environment

- CPU: 13th Gen Intel Core i7-1355U, 12 logical cores (host shared with desktop)
- RAM: 16 GB
- Kernel: 7.1.5+kali-amd64 (Linux)
- Docker 28.5.2, Compose 2.40.3
- Go 1.23.4, Python 3.13.5, Node v24.20.0, k6 v0.54.0
- Engine version: 1.0.0
- Containers run without CPU or memory limits; the host is also running the
  analyst dashboard and the test tooling, so absolute numbers include that
  contention.

## Methodology

- Each scenario is generated by a k6 script in `bench/k6/` and orchestrated by
  `scripts/bench_run.py`.
- Server-side percentiles are read from decision-api `/metrics` histogram
  deltas before and after each run. The Prometheus container exits 127 in this
  environment, so no Prometheus storage is involved.
- Every run records the command line, git sha, engine version, dataset hash,
  seed and config hash in `bench/results/<date>/`.
- S1 ran three times; its report contains all three runs. Scenarios S2–S9 were
  not run in the release window and are explicitly NOT_RUN rather than inferred.

## S1 steady (1,000 rps, 60 s, rules + ML)

Measured on 2026-11-19, three consecutive runs:

| run | requests | p50 ms | p95 ms | p99 ms | p99.9 ms | errors |
|---|---|---|---|---|---|---|
| 1 | 59,816 | 41.86 | 63.65 | 90.08 | 129.02 | 0 |
| 2 | 59,859 | 43.40 | 68.61 | 85.22 | 113.33 | 0 |
| 3 | 59,819 | 47.69 | 76.93 | 98.37 | 137.61 | 0 |
| median | 59,819 | 43.40 | 68.61 | 90.08 | 129.02 | 0 |

Target: p99 < 50 ms. **Not met on this hardware.** All three runs returned zero
HTTP errors, but the decision pipeline degraded every request through
`FEATURE_TIMEOUT` (142,044 cumulative `fade_fail_policy_total{cause="FEATURE_TIMEOUT",mode="step_up"}`):
the feature stage averaged ~23.8 ms against a 20 ms budget, and the ML stage
averaged ~20.6 ms. The client p99 is therefore a degraded-mode latency, not a
full-pipeline latency.

Bottleneck: the feature Lua script does up to three Redis round-trips per
P2P/bank-transfer event for cycle detection; at 1,000 rps with accumulated
account state those calls queue. At 200 rps p95 is ~6 ms, so the limit is
queueing, not per-request service time.

Mitigations already in the tree: reduced cycle caps (max_neighbors 50→10,
max_visited 200→30, time_budget 3→1 ms), Redis pool 256 / min-idle 64, ML
scorer single-threaded with a vectorised `/score/batch`, and Go micro-batching.

Remaining levers (not applied: they either change decisions or need a retrain):
move cycle detection into one Lua script; reduce IsolationForest trees.

Measured ceiling on this hardware: ~90 ms p99 at 1,000 rps. The target is
recorded as failed, not relaxed. See `docs/known-issues.md`.

Evidence: [`bench/results/2026-11-19/s1.json`](../bench/results/2026-11-19/s1.json),
[`s1.md`](../bench/results/2026-11-19/s1.md).

## Detection evaluation (partial window)

The replay of the full 90-day evaluation set did not finish: replay is
CPU-bound in feature computation at ~15 events/s on this host, so a 5% account
sample would have taken over five hours. A one-day window (68,800 events, 207
fraud events) was analysed instead.

| config | recall | 95% CI | FPR | precision | recall @ ≤1% FPR |
| --- | --- | --- | --- | --- | --- |
| rules-only | 87.9% | 82.8–91.7% | 1.34% | 16.5% | 70.0% |
| combined | 88.9% | 83.9–92.5% | 1.34% | 16.7% | 70.5% |
| ML-only | 90.3% | 85.5–93.7% | 1.34% | 16.9% | 72.9% |

Targets: recall at ≤1% FPR ≥ 85%, lift ≥ +10 points, FPR ≤ 1%. All three miss
in this window; the confidence intervals are wide because only 207 fraud events
were scored. Per-scenario recall:

| scenario | fraud events | combined recall (95% CI) |
| --- | --- | --- |
| AGENT_FRAUD | 9 | 33.3% (12.1–64.6%) |
| ATO_SIMSWAP | 8 | 50.0% (21.5–78.5%) |
| STRUCTURING | 120 | 100.0% (96.9–100.0%) |
| VELOCITY | 70 | 81.4% (70.8–88.8%) |

Worst-segment FPR ratio is 2.39× (target ≤ 2×). Evidence:
[`bench/results/2026-11-19/detection.json`](../bench/results/2026-11-19/detection.json).

## Failure-mode and chaos runs

`bench/chaos/run.sh` exercises C1–C14 and writes
[`chaos.json`](../bench/results/2026-11-19/chaos.json). C1–C7, C10, C12–C14 pass.
C8 (network partition), C9 (disk full) and C11 (clock skew) need root,
`CAP_NET_ADMIN`, a loopback mount or a host clock change and are reported as
NOT_RUN with their reason. C1 and C4 were the two real defects found by the
harness; both have fixes with regression coverage in the harness.
